# TeacherPro — личный кабинет преподавателя

Веб-приложение для личного использования: расписание, ученики, абонементы и оплаты. Развёртывается на Vercel, облачные данные хранятся в Supabase.

## Что реализовано
- Главная панель с цветными карточками показателей, быстрыми действиями, ближайшими занятиями, ожидаемыми оплатами и абонементами, требующими внимания
- Адаптивный дашборд для компьютера и телефона с отдельным пустым состоянием и пошаговым началом работы
- Недельный календарь с быстрым созданием и редактированием занятий
- Проверка пересечений занятий с учётом длительности, подтверждение конфликтов и выбор длительности 30–120 минут
- Подтверждение отмены занятия и корректировка списаний при смене статуса или ученика
- Повторяющиеся занятия: каждую неделю или раз в две недели
- Расширенная карточка ученика: контакты и заметки, ближайшее занятие, история занятий и оплат, полученные и ожидаемые суммы, активный абонемент
- Отдельные абонементы со стоимостью, сроками и остатком занятий
- Учёт оплат, включая ожидающие поступления; отметка оплаты как полученной/ожидающей, удаление ошибочной записи и обзор записей с датой в прошлом
- Автоматическое списание занятия при переводе в статус «Проведено» и возврат при отмене/переводе обратно
- Регистрация, вход, повторное письмо подтверждения и восстановление пароля
- Синхронизация через Supabase и индикатор состояния в интерфейсе
- Экспорт и импорт резервной копии JSON
- Установка как PWA и кэширование оболочки приложения для повторного открытия
- Адаптивная мобильная навигация
- Аналитика дохода за последние 6 месяцев и счётчики проведённых/отменённых занятий
- Внутренний список задач: ожидаемые оплаты, абонементы с малым остатком и скорым окончанием срока, занятия на сегодня
- Автоматическая защита от повторного списания одного занятия при повторном вызове логики списания

## Архитектура
- Frontend: HTML, CSS, JavaScript
- Хостинг: Vercel
- Auth + cloud storage: Supabase Auth и таблица `public.app_data`
- Row Level Security: пользователь может читать и менять только собственную строку
- В браузере остаётся локальная копия, а облако является основной версией после входа

## Supabase setup
1. Создай Supabase-проект.
2. В SQL Editor выполни актуальный `supabase/schema.sql` **повторно после обновления**: SQL добавляет триггер серверной версии записи и настраивает RLS и права. Изменение файла в GitHub **само не меняет** уже существующую базу Supabase. Перед применением SQL сохрани резервную копию базы.
3. В Project Settings → API возьми Project URL и публичный publishable/anon key.
4. Заполни `cloud-config.js` значениями `RITM_SUPABASE_URL` и `RITM_SUPABASE_ANON_KEY`. **Никогда не помещай сюда service_role/secret key.**
5. В Authentication → URL Configuration укажи основной URL приложения в Site URL и добавь его в Redirect URLs.
6. В Authentication → Providers → Email можно временно отключить Confirm email для входа сразу после регистрации. Для обязательного подтверждения включи Confirm email; настрой Site URL и Redirect URLs из шага 5, а для реальной эксплуатации подключи собственный SMTP (встроенная почта Supabase строго ограничена по частоте). Приложение поддерживает оба режима и повторную отправку письма с интервалом не менее 60 секунд. Подтверждение должно обеспечиваться Supabase на сервере, не только интерфейсом.
7. Push в ветку `main` автоматически запускает деплой Vercel.

## Работа с данными
- Новый аккаунт начинает с пустого списка учеников, без демонстрационных клиентов.
- При первом входе нового пользователя создаётся пустая база. Локальная копия хранится по отдельному ключу для каждого user ID, а не общему для всех аккаунтов.
- Если облачная запись существует, она загружается на устройство.
- Экспортируй резервную копию перед массовым импортом или очисткой.
- Синхронизация отправляет изменения с небольшой задержкой, используя `updated_at` как версию записи: при параллельных изменениях приложение блокирует перезапись более новой облачной версии. Автоматического слияния изменений пока нет.
- Несинхронизированные изменения сохраняются локально для конкретного аккаунта (включая версию, от которой были сделаны правки) и восстанавливаются после повторного входа.
- Если возник конфликт версий, открой «Настройки»: скачай резервную копию локальных данных и выбери «Загрузить облачную версию (с резервной копией)» — это заменит локальную версию. Чтобы сохранить локальные правки, экспортируй JSON, затем загрузи актуальную облачную версию и вручную перенеси изменения или импортируй резервную копию целиком (при импорте текущие данные заменяются).
- Локальное хранилище браузера не зашифровано: не используй общедоступные устройства, очищай профиль браузера при передаче устройства другому человеку.
- При ошибке синхронизации проверь индикатор в верхней панели. Не считай данные сохранёнными в облаке, пока статус не подтвердит синхронизацию.

## Локальный запуск
Нужен локальный HTTP-сервер (не открывай HTML как `file://`, иначе Supabase/PWA могут работать некорректно):

```bash
python -m http.server 8080
```

Открой http://localhost:8080.

## Альтернативный хостинг без домена Vercel

Добавлен GitHub Actions workflow `.github/workflows/pages.yml`. После включения GitHub Pages сайт можно публиковать по адресу `https://xchestikov.github.io/teacherpro/`.

1. Открой Settings репозитория → Pages.
2. В разделе Build and deployment выбери **GitHub Actions** как источник.
3. Дождись workflow **Deploy static app to GitHub Pages** в разделе Actions.
4. В Supabase → Authentication → URL Configuration добавь в Redirect URLs адрес `https://xchestikov.github.io/teacherpro/**`.
5. Открывай сайт по GitHub Pages URL и проверь вход, письмо подтверждения и сохранение данных.

Это альтернативный адрес frontend. Если без VPN недоступен именно API Supabase, перенос frontend сам по себе этого не исправит — тогда понадобится отдельно проверить доступность `egopcojrzklvytcuhpov.supabase.co` и, возможно, сменить backend/провайдера.


## Предоплата абонементов
- При создании нового абонемента можно указать, оплачен ли он авансом или ожидает оплаты.
- Создание абонемента создаёт связанную запись в истории оплат; сумма учитывается в доходе только при статусе «Оплачено».
- Оплата привязана к конкретному абонементу. Изменение статуса оплаты синхронизируется с ним, повторная запись не создаётся при редактировании абонемента.
- Проведённое занятие списывается из оплаченного остатка; занятие нельзя впервые отметить проведённым, если нет оплаченного остатка.
- Нельзя удалить связанную запись предоплаты или вернуть её в ожидание, если по этому абонементу уже списывались занятия.
- Для старых данных, где у абонемента ещё нет поля статуса оплаты, сохраняется совместимость: такие абонементы считаются оплаченными.

## Пароли
- При новой регистрации и смене пароля требуется 8–72 символа, хотя бы одна буква и одна цифра, без пробелов, и подтверждение пароля.
- При входе существующие пароли не блокируются клиентской проверкой по новым правилам.
- Проверка в браузере нужна для удобства: для строгого серверного минимума отдельно настрой требования пароля в Supabase Auth (минимум 8 символов).

## Проверка безопасности и синхронизации
1. Проверь в Supabase Database → Tables → `app_data`, что RLS включён. Применить SQL из `supabase/schema.sql` необходимо вручную в правильном проекте.
2. Зарегистрируй два тестовых аккаунта. Ученик из первого аккаунта не должен появляться во втором. Проверь чтение и запись с обеих сессий.
3. Открой один аккаунт в двух разных браузерах, измени один и тот же профиль в каждом, сохрани сначала в первом, затем во втором. Во втором появится предупреждение о конфликте, а облачная версия первого не должна быть перезаписана.
4. Для проверки офлайна открой приложение, отключи интернет, внеси изменение, затем включи интернет. После успешной синхронизации оно должно появиться на другом устройстве. Если второе устройство успело обновить облако, появится конфликт.
5. При конфликте сначала экспортируй локальную резервную копию в «Настройках». После выбора облачной версии локальные изменения будут заменены.
6. Пользовательские данные могли быть перенесены между аккаунтами **до** исправления. Их нужно отдельно проверить в Supabase и при необходимости исправить вручную после резервного копирования. Новая логика не удаляет старые загрязнённые записи.

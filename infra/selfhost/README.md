## Условие следующего этапа

1. Увеличить параметры **этого же VPS**, сохранив его данные, публичный IP, панель и сайт. Рекомендуем **4 vCPU / 8 ГБ RAM / 80 ГБ SSD**; минимальная конфигурация **2 vCPU / 4 ГБ RAM / 40 ГБ SSD** годится только с проверкой реальной нагрузки.
2. Проверить, что увеличение диска действительно выполнено и файловая система расширена: `lsblk`, `df -h`; наличие нового виртуального диска не означает расширение корневой ФС. Перед изменением размера сделать снимок/бэкап у провайдера.
3. Подтвердить работающий **независимый административный SSH** (ключи и sudo/root через консоль провайдера), не ломая действующего `teacherpro-deploy`. **Не отключать root/password SSH и не менять firewall, пока не проверен резервный доступ.**
4. Установить Docker Engine + Compose из официальных пакетов с закреплённой версией, защитить интерфейсы и группы прав. Не добавлять пользователя деплоя в `docker`, если ему не должны принадлежать root-права: доступ к Docker daemon равносилен привилегированному доступу к хосту.
5. Запустить `sudo bash infra/selfhost/host-preflight.sh` (только чтение); должен завершиться с кодом 0. Если запускается через sudo, Docker доступность нужно проверять от администратора. При ошибке не продолжать.

## Развёртывание — только после preflight

Официальная инструкция: https://supabase.com/docs/guides/self-hosting/docker.
Использовать **production Docker Compose**, а не тестовую CLI-оболочку `supabase start`.

1. Администратор скачивает и **проверяет** конкретный релиз `supabase/supabase` и его `docker/`-конфигурацию. Зафиксировать release commit и версии image tags. Не выполнять вслепую `curl | sh`.
2. Разместить вне директории сайта, например `/opt/teacherpro-supabase`. Генерировать уникальные DB password, publishable key, secret key и JWT signing keys; секреты хранить в `root`-доступном `.env` с правами `0600`, **никогда не коммитить и не печатать в GitHub Actions**.
3. Использовать Supabase Postgres 17 для совместимости с исходной версией 17 (сверить подходящую версию образа и официальный PG17 upgrade guide). Не монтировать старые данные в контейнер, инициализировать отдельную пустую БД.
4. Supabase gateway, Studio, PostgreSQL и Supavisor должны **слушать только loopback или внутреннюю сеть Docker**, без открытых TCP 5432/8000 и панели Studio в интернет. При необходимости тестирования открыть временный SSH tunnel. Nginx на 443 пока должен проксировать на старый Supabase: **не менять существующий конфиг до cutover**.
5. Убедиться в `docker compose ps` (все компоненты healthy), тестовом создании пользователя и защищённой локальной API-проверке. Настроить SMTP для писем авторизации и восстановления, SITE_URL и допустимые redirects `https://teacherpro-app.ru/**`.
6. Включить **шифрованные бэкапы** Postgres + Auth + локальных Storage-объектов + критичных конфигов (без раскрытия ключей). Должна быть копия **в другом российском хранилище**, не только на этом VPS. Проверить восстановление на изолированном экземпляре.

## Перенос данных: auth, public, Telegram, роли, RLS

Официальная процедура: https://supabase.com/docs/guides/self-hosting/restore-from-platform.

- Не экспортировать реальные записи в GitHub issue, Actions log, артефакты без шифрования или в публичные ветки. Дамп содержит ФИО учеников, платежи и хеши паролей.
- Работать с защищённой административной машиной/сервером; доступы к базе хранить в хранилище секретов.
- Использовать **Supabase CLI `db dump` по официальной инструкции**, раздельно роли, схема, данные; raw `pg_dump` полного managed проекта не является безопасной заменой (включает платформенные системные объекты). Из-за различий managed Postgres 17 и self-hosted Auth/Storage провести сначала пробное восстановление.
- Сверить `infra/selfhost/verify-counts.sql` на обеих сторонах. В источнике на момент предварительной проверки: 4 пользователя Auth, 3 строки app_data, 3 Telegram links, 13 Telegram invites, 0 Storage objects; данные могут меняться, поэтому это **не** фиксация для cutover.
- Убедиться, что сохранены email/password-хеши и идентификаторы `auth.users.id`, все RPC, RLS, роли, admin permissions, Realtime policies и таблицы `tp_*`. Проверить, что пользователи не получают доступ к чужим кабинетам.
- Заново настроить Auth, SMTP, API keys, JWT. **Старые refresh/access токены не будут действовать** после перехода на новые ключи; предусмотрен повторный вход.
- Проверить Telegram связки, invite tokens, запросы и отправку напоминаний на **тестовых** чатах; бот использует service-role credential из закрытой конфигурации на сервере, который потребуется заменить. Не отправлять реальные напоминания из тестового экземпляра.
- Старое приложение продолжает принимать изменения вплоть до финального окна миграции. Перед переключением нужен короткий write freeze, **повторный финальный dump + restore** и проверка, чтобы не потерять финальные правки пользователей.

## Переключение и откат

1. Удостовериться, что `app_data`, платежи, уроки, Telegram и Auth сходятся между источником и локальным контуром, резервные копии восстановлены в тесте и новый API работает через HTTPS.
2. Утвердить техническое окно только после всех тестов. **Не переключать только frontend, оставляя Telegram-бота на старой БД:** получится рассинхронизация.
3. Одновременно обновить API base URL и publishable key на сайте, конфигурации админки, URI/ключ бота, настроить Nginx upstream на loopback Supabase. Проверить интеграции и логин, не отключать существующий origin заранее.
4. Если тесты не пройдут — откатить маршрут и конфиги. **После начала записей в новую БД простой откат маршрута не безопасен без сверки/обратного переноса**; нужен чёткий план недопущения split-brain.
5. Только после миграции и согласования документов по 152-ФЗ решить дальнейшую судьбу зарубежного Supabase-проекта и его резервных копий; учесть сроки удаления и трансграничную передачу в рамках применимых требований.

## Почему нужна полная миграция

TeacherPro использует `supabase.auth`, PostgREST `public.app_data`, Realtime, административные таблицы, Telegram табличные данные и серверные RPC. Один новый пустой PostgreSQL без Auth/API не заменяет действующий Supabase. Сейчас на 1 CPU/956 МБ опасно пытаться развернуть даже урезанный рабочий стек.

## Чего этот этап НЕ делает

Не устанавливает Docker, не меняет Nginx/DNS, не экспортирует реальные PII, не редактирует Supabase, не разворачивает новую БД, не вырубает сайт и бота. После изменения тарифа FirstVDS и подтверждения административного доступа можно выполнить развёртывание на этом сервере.
